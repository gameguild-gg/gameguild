## Summary

Moves Pyodide (Python-in-WASM) execution off the main thread into a dedicated, typed Web Worker bridge, fixing the problems raised in #111: the jsdelivr-style script embedding that lost types, DOM-based load/unload, and `runPythonAsync` on the main thread whose `Promise.race` timeout could never actually stop a blocked interpreter.

### What ships

- **Typed worker protocol** (`apps/web/src/components/block-content-editor/extras/code-studio/runners/pyodide-worker/protocol.ts`): compile-time-checked request/response/event discriminated unions with id correlation, config payload and sentinel error classes (`PyodideWorkerInfrastructureError`, `PyodideExecutionTimeoutError`) — no more untyped globals.
- **Worker entry** (`pyodide.worker.ts`): its own webpack chunk (`pyodide-runtime`, same `new Worker(new URL(...), { type: 'module' })` pattern as the Emception toolchain worker). Loads the gzipped Pyodide bootstrap via fetch + `pako` gunzip + blob dynamic import (`pyodide-runtime.ts`) — no DOM `<script>` injection anywhere.
- **Worker core** (`worker-core.ts`): boot/run/interrupt handling, streamed stdout/stderr chunks, batched stdin replay, MEMFS file mapping for multi-file projects — pure logic behind an injected `post`/loader so it is fully unit-testable.
- **Main-thread client** (`pyodide-worker-client.ts`): lazy boot with promise-cached state, id-correlated requests, live `onStdout`/`onStderr`/progress callbacks, SharedArrayBuffer fast-path interrupt, `dispose()` that terminates the worker, and a **hard timeout that terminates the worker and transparently reloads a fresh one on the next run**.
- **`PythonRunner`** (`python-runner.ts`) is now worker-first with **graceful degradation**: when `Worker` is unavailable (or construction/boot fails at the infrastructure level) it falls back to the preserved legacy implementation (`python-runner-main-thread.ts`), so restricted environments keep working.
- **COI headers** (`next.config.ts`): cross-origin-isolated pages refuse workers whose script lacks COEP; added the `pyodide-runtime` chunk rule mirroring the existing `emception-toolchain` one.

### Why not the `comlink` package

The issue suggests comlink. Adding a new runtime dependency risks the dependency-advisory gate (only the three locally-pinned advisories are allowed; new deps can block all CI runs). The in-repo `protocol.ts` + `pyodide-worker-client.ts` pair provides the same expose/proxy-over-postMessage semantics with a fully typed, zero-dependency contract. Swapping in comlink later would be a drop-in change behind `PyodideWorkerClient`'s API.

## Acceptance criteria

- [x] works with the next bundler — `new Worker(new URL('./pyodide.worker', import.meta.url), { type: 'module', name: 'pyodide-runtime' })` (create-pyodide-worker.ts:19) compiles through the repo's webpack pipeline (`next build --webpack`); production build succeeds and emits the dedicated chunk `static/chunks/pyodide-runtime.<hash>.js`; COI header rule for the chunk added in `apps/web/next.config.ts` (source `/_next/static/chunks/:file(pyodide-runtime.*)`).
- [x] load pyodide and emception properly — Pyodide now loads inside the worker via fetch + gunzip + blob import with no DOM embedding (`pyodide-worker/pyodide-runtime.ts:loadPyodideRuntime`); Emception already loads through its worker-backed browser client on develop (`tools/emception/packages/browser/src/boot.ts:bootInWorker` + `worker-client.ts`), untouched by this PR.
- [x] be able to use webworker to wrap and isolate issues. suggestion "comlink" — all Pyodide execution is isolated in the `pyodide-runtime` worker; main thread only exchanges typed messages (`pyodide-worker/protocol.ts`). Implemented as an in-repo typed RPC instead of the comlink dependency to avoid new-dependency advisory-gate risk (same expose/proxy semantics; see note above).
- [x] get/set stdin/stdout for testing automation purposes and assignment validations — stdin is passed per run and replayed line-by-line into `setStdin` (`worker-core.ts` `handleRun`); stdout/stderr stream as id-routed events before the terminal `runOk` (`worker-core.test.ts` "executes code, replays stdin line by line and streams stdout/stderr"; `pyodide-worker-client.test.ts` "streams stdout/stderr chunks through the run callbacks before completion"); `PythonRunner` maps them to `RunnerOptions.onOutput` (`python-runner.test.ts` "streams worker stdout/stderr into onOutput and progress into onProgress").
- [x] extra: have a timeout for the function to execute, otherwise, kill the worker and reload it — `PyodideWorkerClient.handleTimeout` terminates the worker (the only reliable way to stop a blocked WASM interpreter) and the next call transparently boots a fresh worker (`pyodide-worker-client.ts`; proven by `pyodide-worker-client.test.ts` "terminates the worker on timeout and transparently reloads it on the next run" and the runner-level `python-runner.test.ts` "hard-times-out: terminates the worker, returns exit code 1, reloads for the next run").
