## Module shape at a glance

- **36 .cs files** under `Pages:/`: 5 controllers, 17 command records (all with handlers — thin delegation to 5 services), 0 query records (reads go service-direct from controllers), 5 services, 5 entities, 5 entity configurations + `PagesModelConfiguration`, 1 audit port (`IContentPagesAuditEventSink`), DTO + mapping files.
- **32 routes** (`PageController` 15, `ContentResourceController` 7, `CourseProposalsController` 6, `MarketingLeadController` 3, `OpenGraphController` 1). 8 of them are `[AllowAnonymous]` and registered in the host anonymous-endpoint allowlist (`API:/Security/AnonymousEndpointRegistry.cs:98-102,196-198`).
- **Tables (5, default schema)**: `pages`, `page_sections`, `content_resources` (migration `20260210113401_AddContentPagesModule`), `marketing_leads` (`20260512031314_AddMarketingLeads`), `course_proposals` (`20261015015009_AddCourseProposals`). Model applied via `PagesModelConfiguration : IModelConfiguration` (`Pages:/Configuration/PagesModelConfiguration.cs:9-17`) discovered by assembly scan (`API:/Database/ApplicationDbContext.cs:866-883`).
- **Wiring**: module services registered by `AddContentPagesModule` (`Pages:/Configuration/PagesModule.cs:13-22`) called from the host (`API:/Core/Setup/InfrastructureLayerExtensions.cs:335`); command handlers register via the CQRS assembly scan (`API:/Core/Setup/ApplicationLayerExtensions.cs:142` → `AddCqrs`, module enabled per `API:/Core/Setup/ModuleConfiguration.cs:24`); the audit-sink implementation is supplied by Compliance.Audit (`Audit:/Extensions/AuditModule.cs:142`).
- **Auth**: class-level `[Authorize]` on `PageController`/`ContentResourceController` (with code-level `ActorContext.HasAnyPermission` gates — see C1 for where they are missing), per-action `[Authorize]`/`[AllowAnonymous]` mix on the other three. No `[EnableRateLimiting]` attributes — every route rides the `global` policy (`API:/Core/Extensions/RateLimitingServiceCollectionExtensions.cs:121`). No policies (`Policies.*`) are referenced; permission keys come from `Authz:/Models/TypedPermissions.cs:202-226`.
- **Tenancy**: pages/resources/proposals/leads are **platform-global** — no tenant query filters in any configuration; `EntityBase.TenantId` stays null and is only echoed into audit events (`Pages:/Services/PageService.cs:78-79`).

## Headline findings

1. **The editorial permission gate covers only `PUT`** — `UpdatePage`/`UpdateSection`/`Update` check `content-edit|write|admin` (`Controllers/PageController.cs:137,243`, `Controllers/ContentResourceController.cs:122`), but `POST` create, `DELETE`, publish, unpublish and every section mutation are guarded by nothing beyond `[Authorize]`: **any authenticated user can create, soft-delete, publish and unpublish pages and content resources** (gap C1; STRIDE E1).
2. **Soft-delete is cosmetic for `Page`/`PageSection`/`ContentResource`** — `DeleteAsync` sets `DeletedAt` (`Services/PageService.cs:126`, `Services/ContentResourceService.cs:133`) but no configuration installs a `HasQueryFilter` and no read predicate checks `DeletedAt` for the aggregate root: deleted pages/resources keep resolving by id and by slug and keep appearing in listings (C2). Only `GetSectionsAsync` filters deleted *sections* (`Services/PageService.cs:169`).
3. **`ScheduledPublishAt` is inert** — both `Page.ScheduledPublishAt` (`Entities/Page.cs:166`) and `ContentResource.ScheduledPublishAt` (`Entities/ContentResource.cs:176`) are stored, but no background worker or command ever promotes a scheduled page; the field is decoration (C3). (Contrast: `Resources.Contents` has a real Scheduled state — also worker-less, see its package.)
4. **Section sub-resource reads leak draft pages** — `GET pages/{pageId}/sections` and the per-section GET/PUT/DELETE/reorder routes never check the parent page's publication status or `CanViewUnpublished`, so any authenticated caller can enumerate the blocks of an unpublished page (C4); the by-id/by-slug page endpoints *do* enforce the draft 404 (`Controllers/PageController.cs:65-68`).
5. **Marketing-lead states are unreachable and PII has no erasure path** — `MarketingLeadStatuses.Reviewed/Archived` (`Entities/MarketingLead.cs:21-31`) have no mutating route (CRM surface is read-only), and the lead table stores name/email/company/message with no delete or retention route (C6).
6. **Audit is the module's one strong property** — every mutation writes a required audit event in the owning transaction and fails closed through `SaveWithRequiredAuditAsync` (`SharedKernel/Abstractions/AuditedMutationExtensions.cs:62`) → `CentralContentPagesAuditEventSink` (`Audit:/Services/CentralModuleAuditEventSinks.cs:56-86`); proposal/lead audit events record shape, never submitted values (`Services/CourseProposalService.cs:27-34`, `Services/MarketingLeadService.cs:29-35`). The E9 route smoke shows **zero** 5xx for this module's 32 routes (no `E9|` baseline entries mention `pages`, `content-resources`, `marketing`, `course-proposals` or `/og`).
