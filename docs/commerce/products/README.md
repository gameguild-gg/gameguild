# GameGuild.Commerce.Products — Documentation Package

> Module `GameGuild.Commerce.Products` (+ pricing experiment/rule entities in `GameGuild.Commerce` and the host composition that wires it) · Documented against `develop` commit `60100459e6` (merge of #1283).
> **Post-#1290 status**: the wiring gaps P1–P4 documented here are fixed — the host composes `AddProductsModule` (`API:/Core/Setup/InfrastructureLayerExtensions.cs` block 10c) and the module binds its four options sections. `ProductSubscriptionPlan` (P5) is deprecated by documentation (do not read/write/extend; removal is a billing-orders follow-up).
> Scope: the product catalog and monetization surface — browse/detail/search, catalog administration (create/update/batch/lifecycle, categories, bundles, inventory), pricing display (versioned `ProductPricing`, pricing rules, tiers, A/B pricing experiments), the promo engine (codes, campaigns, stacking, usage, attribution, CAPTCHA/anomaly defenses), user-product entitlements, and the in-app support-ticket system the module also hosts. The price-source-of-truth contract with subscription billing post-#1266 is documented explicitly (`05-cross-module-sequences.md` §5).

- **Entities (25 files)**: `Product` (+ `ProductCommissionConfig`, `ProductBundleItem`, `ProductInventory`), `ProductCategory` (hierarchical, tenant-unique slug), `ProductPricing` + `ProductPricingVersion` (immutable price history), `PricingTier`, `ProductSubscriptionPlan` (**deprecated orphan — no reader/writer; see `06-gaps.md` P5**), `UserProduct` (access rows), `PromoCode`/`PromoCampaign`/`PromoCodeUse`/`PromoCodeUserUsageCounter`/`PromoCodeValidationAttempt`/`PromoCampaignAttribution`/`PromoStackingRule`/`PromoValidityWindow`/`PromoCustomerType`, `SupportTicket`(+Message); pricing rules & experiments live in `Commerce:/Entities/` and are configured by the Products module (`Products:/ProductsModule.cs:268-349`).
- **Services**: `PricingEngineService` (effective price → rule discount → experiment arm → promo codes, `Products:/Services/PricingEngineService.cs:10-120`), `PromoCodeService` + gates (`PromoRedemptionCaptchaGate`, `PromoUsageAnomalyEvaluator`, `PromoCustomerStateResolver`), `EntitlementService`, `UserProductService`, `ProductCategoryValidator`, `BundleSavingsCalculator`, `PricingExperimentService` (+ sticky `PricingExperimentAllocator`), plus the two cross-module coordinators `SubscriptionPromoCoordinator` and `FraudReviewSupportTicketCoordinator`.
- **Background service (1)**: `PricingSchedulingBackgroundService` (issue #395 scheduling sweep — hosted by the composed API since the #1290 fix; **at the documented commit `60100459e6` it was never hosted**, P1).
- **Wiring reality** (the package's central finding, updated for #1290): handlers/validators register via module scan (`API:/Core/Setup/ApplicationLayerExtensions.cs:110-145`, `Commerce.Products` in `ModuleConfiguration.CommonEnabledModules:20`); repositories and `I{Name}Service` register by the host's convention scanner (`API:/Core/Setup/InfrastructureLayerExtensions.cs:482-560`); everything else — the hosted scheduler, the four `.Bind(...)`-wired options classes, the five promo-engine/defense services and the six non-convention promo/pricing/catalog services — registers through `AddProductsModule` (`ProductsModule.cs:16-66`), which the host composes at `InfrastructureLayerExtensions.cs` block 10c. **At `60100459e6` that call did not exist**: the scheduler, options bindings and five services were absent from the composed host (`02-cqrs-wiring-matrix.md` §0, `06-gaps.md` P1-P4).

## Headline findings

> Findings 1–4 describe `develop@60100459e6` and are **fixed by #1290** (the host now composes `AddProductsModule` with bound options; the total promo-rejection throw is a `DomainException` → 422). They are kept for history and for the fix's regression tests.

1. **`AddProductsModule` had no host caller** (`ProductsModule.cs:16` — only the unit test called it): the pricing scheduler never ran, `PricingSchedulingOptions`/`PromoEngineOptions`/`PromoAbuseDetectionOptions`/`PromoRedemptionCaptchaOptions` bound to nothing (not even the module bound sections — `AddOptions<T>()` without `.Bind`), and five promo services were unregistered (`06-gaps.md` P1).
2. **Subscription creation with promo codes failed hard** — `CreateSubscriptionCommandHandler` threw when `ISubscriptionPromoCoordinator` was null and promo codes were supplied (`Subs:/Commands/CreateSubscription/CreateSubscriptionCommandHandler.cs:83-87`); the coordinator implementation existed but was only registered by the never-called module method (`ProductsModule.cs:36`). Fail-closed, as an unplanned 500 (`06-gaps.md` P2).
3. **Fraud-review tickets silently skipped** — `ProcessPaymentCommandHandler` and `SubscriptionChangeFraudGate` take `IFraudReviewTicketCoordinator? = null` (`Payments:/Commands/ProcessPayment/ProcessPaymentCommandHandler.cs:27`, `Subs:/Commands/SubscriptionChangeFraudGate.cs:66`); with the coordinator unregistered, issue #409's "reviews surface in the support queue" behavior quietly never happened (`06-gaps.md` P3).
4. **Anti-farming/anti-abuse defenses were off** — the CAPTCHA gate, the usage-anomaly evaluator and the customer-state resolver were optional constructor params that resolved to null in the host, so anonymous promo probing was ungated and customer-type-restricted codes failed closed as `CustomerNotEligible` (`Products:/Services/PricingEngineService.cs:312-318`, `06-gaps.md` P4). Post-#1290 defaults: anomaly evaluator and customer-state resolver active; CAPTCHA gate registered but opt-in (`PromoRedemptionCaptcha:Enabled=false`, fails closed when enabled).
5. **Price source of truth post-#1266 is the plan, not the product** — subscription billing amounts derive from `SubscriptionPlan.MonthlyPriceInCents` via `SubscriptionPlanPricingResolver` (`Subs:/Services/SubscriptionPlanPricingResolver.cs:30-62`) and the payment handler rejects any mismatch (`Payments:/Commands/ProcessPayment/ProcessPaymentCommandHandler.cs:50-53`); `ProductPricing` is catalog/display pricing only, and `ProductSubscriptionPlan` is a **deprecated** orphan table nothing reads. Consistency between what the catalog displays and what is billed is a UI discipline, not an enforced invariant (`05-cross-module-sequences.md` §5, `06-gaps.md` P5/P6).
