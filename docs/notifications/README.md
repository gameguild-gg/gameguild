# GameGuild.Notifications — Documentation Package

> Module `GameGuild.Notifications` · Documented against `develop` commit `ce31d5850c` (merge of #1311).
> Scope: **the cross-cutting delivery module every other module depends on** — the notification lifecycle (`Pending → Sending → Sent / DeadLettered`, plus `HeldForDigest`), preference management with the delivery-decision chain (Send / HoldUntil / Digest / Drop — including the `whatsAppEnabled` explicit-opt-in saga of #54/#55), the email renderer registry pattern (renderers registered by *producer* modules), the six background dispatcher workers (email, digest, SMS, push, WhatsApp, WhatsApp-broadcast scheduler), retry/backoff/DLQ semantics with admin requeue, SES/SNS delivery-event ingestion with the suppression engine, and the public one-click unsubscribe.

## Module shape at a glance

- **~79 files** under `Notif:` (10.6k LOC): 5 controllers (26 routes), 6 command files (all handlers live), 4 service families (`NotificationService` facade over `NotificationDeliveryService` + `NotificationPreferenceService` + `NotificationTemplateService`; email pipeline incl. renderer registry, dispatchers, digest engine, webhook, unsubscribe; SMS/push/WhatsApp pipelines), 6 entities, 3 EF configurations bridged by one `NotificationsModelConfiguration : IModelConfiguration` (`Notif:/Configuration/NotificationsModelConfiguration.cs:8-14`).
- **Channel topology**: rows are typed `NotificationChannel` (InApp 0 / Email 1 / Push 2 / Sms 3 / Slack 4 / Discord 5 / Webhook 6 / WhatsApp 7 — `Entities/Notification.cs:525-553`); InApp rows are marked Sent at creation (`NotificationDeliveryService.cs:121-125`); every other channel is swept by its own background worker: Email (30s, batch 50), Digest (15m), Sms, Push, WhatsApp, WhatsAppBroadcastScheduler (`NotificationsModule.cs:40,47,55,62,79,87`).
- **Renderer registry**: `EmailRendererRegistry` builds a `Dictionary<NotificationType, IEmailRenderer>` from DI (`Notif:/Services/Email/EmailRendererRegistry.cs:9-15`); renderers are registered **by the producing modules** — Notifications itself only 2 (Security, TenantInvite), Identity.Authentication 10, Commerce.Billing 2, Commerce.Subscriptions 1 (`Authentication/Extensions/DependencyInjection.cs:53-62`; `Billing/Extensions/ServiceCollectionExtensions.cs:72,123`; `Subscriptions/Extensions/DependencyInjection.cs:178`). Missing renderer = permanent config error → dead-letter (`EmailDispatcherService.cs:137-144`).
- **Preference resolution chain** (fixed order, gate-then-route, `Notif:/Services/NotificationPreferenceService.cs:150-244`): 0 WhatsApp explicit opt-in (fail-closed, even for urgent/transactional) → 1 transactional/urgent bypass → 2 per-type mute → 3 channel toggle → 4 category toggle → 5 digest routing → 6 quiet hours (InApp drops, Email holds, others send).
- **Retry/DLQ**: attempt-count backoff schedule `[1m,5m,30m,2h,8h]`, `MaxAttempts 5`, transactional staleness TTL 24h, Sending-reclaim after 10m (`EmailDispatcherOptions.cs`; `EmailDispatcherService.cs:24,34,100-108`); dead letters requeueable by admin with audit counters (`Notification.MarkRequeued`, `Entities/Notification.cs:312-325`).
- **Wiring**: `Notifications` is in `CommonEnabledModules` (`API:/Core/Setup/ModuleConfiguration.cs:35`) — handlers scan-registered; `AddNotificationsModule` called by the host at `API:/Core/Setup/InfrastructureLayerExtensions.cs:340`.
- **Auth**: `NotificationsController` `[Authorize]` self-scoped; `EmailDeliveryAdminController` + `WhatsAppBroadcastAdminController` `[Authorize(Policy = Policies.Admin)]` (`Authz:/Policies.cs:111`); the SNS webhook and the unsubscribe endpoint are `[AllowAnonymous]` by design (signature/token verified instead).

## Headline findings

1. **The email dispatcher still evaluates preferences with the legacy boolean gate** — `EmailDispatcherService.DispatchAsync` re-checks `ShouldSendNotificationAsync` ([Obsolete], `NotificationPreferenceService.cs:246-256`) and treats *any* false as a 30-minute hold (`PreferenceHoldRecheckInterval`, `EmailDispatcherService.cs:28-31, 110-127`). The decision-based API (`DecideDeliveryAsync`) already ran at row creation; the re-check is an interim double-gate that can hold *transactional-bypassed* rows (the bypass lives only in `DecideDeliveryAsync` step 1) — mismatch documented in-code as "INTERIM ... Reconcile" (N1).
2. **28 of 43 notification types have no email renderer** — any Email-channel row of an uncovered type is guaranteed to dead-letter with "No email renderer registered" (`EmailDispatcherService.cs:137-144`). Renderers exist for exactly 15 types; the coverage table is in 04 §3 (N2).
3. **Suppression is enforced at two points with a documented race** — hard bounce/complaint upserts a suppression row and dead-letters all *Pending* rows to the address inside the webhook transaction (`EmailEventProcessor.cs:38-90, 93-135`); in-flight *Sending* rows are caught by the dispatcher's pre-send check (`EmailDispatcherService.cs:157-172`). Client-side normalization exists because `EmailAddressNormalizer` is not SQL-translatable (same EF-translation class as #1278 E9).
4. **The unsubscribe endpoint is a public, anonymous preference mutator** — DataProtection-signed tokens (purpose `notification-unsubscribe-v1`, **no expiry by design**, decision A5) flip `emailEnabled=false`, a category toggle, or append a mute (`UnsubscribeTokenService.cs:9-63`; `UnsubscribeNotificationCommand.cs:35-116`). Token forgery is handled; **token replay is unbounded** and transactional types are correctly un-unsubscribable (`:59-65`) (07 family 4).
5. **One controller lives outside the module** — `SubscriptionNotificationsController` (`api/v1/notifications/subscriptions`, Commerce.Subscriptions) reuses the route namespace for billing delivery records; its `:resend` route is an E9 baseline failure (500 on unknown id) (`Subscriptions/Controllers/SubscriptionNotificationsController.cs:33-60`; `wiring-gap-baseline.txt:249`) (N7).
6. **WhatsApp is fail-closed everywhere** — default `WhatsAppEnabled=false` on preferences (`Entities/NotificationPreference.cs:46,118`), the decision chain drops the channel even for urgent/transactional unless opted in (`NotificationPreferenceService.cs:160-168`), settings validate-on-start fail if Enabled without env credentials (`WhatsAppSettings.cs:118-123`), and the NoOp provider declines every send observably (`NotificationsModule.cs:63-75`).
