# GameGuild.TrustSafety — Documentation Package

> Module `GameGuild.TrustSafety` (+ the content-moderation surfaces it is commonly confused with) · Documented against `develop` commit `ce31d5850c` (merge of #1311).
> Scope: the **internal risk-governance control plane** — signed trust/safety evidence events (moderation, reports, marketplace abuse, wash trading, bounty cycling, ad fraud, account restriction, appeal) ingested into an inbox with replay/version guards, projected into per-subject state + compliance evidence + economy compliance **holds**, and an appeal workflow (submitted → assigned → upheld/overturned). This package also documents **the truth about content moderation** per #1250 N1: TrustSafety hosts *no* text checks; the only automated content safety in the platform is Assets' image classification lane; user-report lifecycles live in Assets (assets), Social.Ratings (reviews), and Learning.Courses (content), each with its own surface.

## Module shape at a glance

- **3 files, 587 lines**: `TrustSafetyModule.cs` (87 — composition + risk input source), `TrustSafetyPersistence.cs` (115 — 3 internal row classes + `TrustSafetyModelConfiguration`), `PostgreSqlTrustSafetyControlPlane.cs` (385 — enums, event/appeal records, signature verifier adapter, `ITrustSafetyControlPlane` implementation).
- **The truth about "disabled"**: `"TrustSafety"` sits in `ApiProductComposition.DisabledModules` (`API:/Core/Setup/ApiProductComposition.cs:113-116`), but that list only feeds `ModuleConfiguration.DefaultDisabledModules` (`ModuleConfiguration.cs:45-46`) whose `IsEnabledAssembly` consults **Enabled** modules only — used solely by the CQRS handler scan, and the module has zero CQRS handlers. Everything else is live: the composition is registered by the economy capability host (`API:/Core/Setup/EconomyCapabilityCompositionExtensions.cs:23`), tables materialized in migration `20260824180312_AddEconomyProductionPlatform` (`:1166-1220` — created via SQL-defined economy platform migration, matched by the assembly-scanned `TrustSafetyModelConfiguration`), and the appeals HTTP surface is carried by the API host (`API:/Core/Controllers/EconomyComplianceAdministrationController.cs:168-235`).
- **What it actually does for the economy**: `PostgreSqlTrustSafetyRiskInputSource` reads the latest `ComplianceEvidenceKinds.TrustSafety` evidence for a subject and maps Approved/Rejected/NeedsReview → Allow/Deny/Review for the economy risk decision issuer (`Econ:/Risk/PostgreSqlEconomyProtectedOperationRiskDecisionIssuer.cs:188-190`) and payout authorization (`Finance.Economy.Payouts/PayoutCoordinator.cs:116`). No evidence (the current permanent state, T1) → outcome `Unavailable` with reason `trust-safety-evidence-unavailable` (`TS:/TrustSafetyModule.cs:40-58`).
- **Content safety reality check (#1250 N1)**: no text moderation exists anywhere in Social; TrustSafety was named as the would-be enforcement host but contains no text checks at all (`docs/social-platform/05-gaps.md:17-18`). The live automated safety lane is `Assets:` image classification through the LiteLLM vision proxy with the 8-label taxonomy and dual thresholds (`API:/Security/LitellmModerationClassifier.cs:34-39`; `Assets:/Moderation/ModerationService.cs:26-58`).

## Headline findings

1. **Both control-plane write surfaces have zero callers** — `IngestAsync` (the only way TrustSafety evidence enters the system) and `SubmitAppealAsync` (the only way an appeal row is created) are invoked by nobody in `Source/` or `tests/` (T1). Consequences: the risk input source can never see evidence (every economy consult maps to `Unavailable`), and the live appeals console (list/assign/decide routes) reads/advances an eternally-empty table.
2. **Text moderation is zero and that is the documented truth** — #1250 N1 (high): user-generated text (posts, comments, blog, reviews' text) flows unchecked; only media is gated (`docs/social-platform/05-gaps.md:17-18`). The `LitellmModerationClassifier` classifies **images only**; its label taxonomy has no text lane (T2).
3. **The appeals console is `[Authorize]`-only** — no `Policies.Admin`, no tenant-permission gate; any authenticated user can attempt assign/decide on appeal ids (404 on miss, 409 on wrong version) (`API:/Core/Controllers/EconomyComplianceAdministrationController.cs:38, 168-235`) (T3). Contrast the Notifications/WhatsApp admin consoles which demand `Policies.Admin`.
4. **The auto-moderation lane has a default-approve trap** — the module-level fallback `UnresolvedModerationClassifier` returns `IsApproved=true, labels=[], "unresolved"` (`Assets:/Moderation/UnresolvedModerationClassifier.cs:8-13`); safe only because the host registers the LiteLLM client; a misconfigured composition silently approves everything it fails to classify (T4, STRIDE family 4).
5. **Report-bombing auto-flags at 3 with no reporter identity stored** — `RatingModerationService.ReportAsync` increments `ReportCount` and flips to `Flagged` at ≥3 (`Ratings:/Services/RatingModerationService.cs:135-152`); the `Reason` is logged but no reporter row exists → unbounded anonymous-ish pressure on any review (STRIDE family 3).
