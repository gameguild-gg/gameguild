# GameGuild.Compliance.FinancialCrime — Documentation Package (AML)

> Module `GameGuild.Compliance.FinancialCrime` (+ its host composition in `GameGuild.API` and the Economy risk engine that consumes its evidence) · Documented against `develop` commit `60100459e6` (merge of #1283).
> Scope: the anti-money-laundering (AML) surface of the platform — sanctions/PEP/adverse-media screening ingestion, transaction-monitoring signals, AML case management (assign/decide), regulatory references (SAR/STR), the financial-crime evidence ledger (kind `financial-crime`), and the money-path gates that consume that evidence (protected-operation risk decisions, HardCoin→SoftCoin conversion, payout eligibility). The AML examiner / FIU / sanctions provider is modeled as an external party throughout.

## Module shape at a glance

- **4 files, ~855 lines, no controllers of its own, no CQRS requests of its own** (`FC:/`): the module is a control plane + persistence + a risk-input adapter.
  - `FC:/FinancialCrimeModule.cs` — `ModuleBase` marker (`EnabledByDefault => true`, `:11`) and `AddFinancialCrimeComposition` (`:18-24`).
  - `FC:/FinancialCrimePersistence.cs` — 7 row types + `FinancialCrimeModelConfiguration` (`:108-208`) → **7 tables** applied by the `ApplicationDbContext` assembly-scanned `IModelConfiguration` pipeline (`API:/Database/ApplicationDbContext.cs:866-883`): `compliance_financial_crime_{screenings, transaction_signals, cases, case_events, decisions, decision_consumptions, regulatory_references}` (snapshot `ApplicationDbContextModelSnapshot.cs:10411-10752`).
  - `FC:/PostgreSqlFinancialCrimeControlPlane.cs` — domain records (`:13-51`), `IFinancialCrimeControlPlane` (`:53-64`, 9 operations), the `Serializable`-transaction PostgreSQL implementation (`:66-396`), validation (`:493-563`), `FinancialCrimeConflictException` (`:568`).
  - `FC:/FinancialCrimeModule.cs:27-79` — `PostgreSqlFinancialCrimeRiskInputSource`, the read-side adapter that turns the latest `financial-crime` evidence envelope into an `ExternalRiskOutcome`.
- **Host composition**: `AddEconomyCapabilityComposition` (`API:/Core/Setup/EconomyCapabilityCompositionExtensions.cs:22`) calls `AddFinancialCrimeComposition` — so the control plane IS registered despite the module name sitting in the host's `DisabledModules` list (`API:/Core/Setup/ApiProductComposition.cs:114-117`); that listing only excludes the assembly from handler/convention scanning (the module has no handlers and no convention-scannable services, so the exclusion is inert — see `06-gaps.md` FC6 on the ambiguity).
- **Host surface**: 5 endpoints on `EconomyComplianceAdministrationController` (`API:/Core/Controllers/EconomyComplianceAdministrationController.cs:46-166`, route `api/v{v}/admin/economy/compliance/financial-crime/*`) backed by three endpoint commands handled by `EconomyComplianceEndpointCommandHandler` (`API:/Core/Commands/EconomyComplianceEndpointCommands.cs:51-77`). Auth: `[Authorize]` + `EconomyPermission.Keys.OperateCompliance` per request (`:232-243`). No rate limiting.
- **Money-path consumers**: `PostgreSqlEconomyProtectedOperationRiskDecisionIssuer` reads financial-crime + trust-safety evidence on every protected operation (`Risk:/PostgreSqlEconomyProtectedOperationRiskDecisionIssuer.cs:182-191`); `HardToSoftConversionRiskEvidenceVerifier` demands fresh `Allow` from both sources (`Risk:/HardToSoftConversionRiskEvidenceVerifier.cs:29-52`, `Risk:/ExternalRiskEvidence.cs:54-78`); `PayoutCoordinator` reads the same evidence for payouts (`Payouts:/PayoutCoordinator.cs:109-116`).

## Headline findings

1. **The AML program has no ingestion** — `IngestScreeningAsync`, `RecordSignalAsync`, `ConsumeDecisionAsync` and `ReadDueRescreeningsAsync` have **no caller anywhere in product sources** (verified by search at `60100459e6`). Cases only open inside the first two (`FC:/PostgreSqlFinancialCrimeControlPlane.cs:118-123, 166-168`), so through the API the case tables can never gain a row: the examiner-facing admin surface operates on a permanently empty program (`06-gaps.md` FC1).
2. **Fail-closed by construction, denied by absence** — with no screenings ever ingested, `PostgreSqlFinancialCrimeRiskInputSource.ReadAsync` returns `Unavailable("financial-crime-evidence-unavailable")` (`FC:/FinancialCrimeModule.cs:53-54`), and every value-moving capability that consults the risk issuer rejects with `ComplianceUnavailable` (`Risk:/PostgreSqlEconomyProtectedOperationRiskDecisionIssuer.cs:82-87`). Enabling Economy value movement today denies every subject on the AML leg — the correct fail-closed posture, but also proof no screening provider is connected.
3. **Three evidence ledgers, one gate that reads only its own** — the KYC pipeline writes kind `kyc-aml`, this module writes kind `financial-crime`, TrustSafety writes kind `trust-safety` (`Risk:/PostgreSqlComplianceEvidenceStore.cs:119-123`). The sign-in KYC gate consults neither economy evidence kind (the compliance package's N7 two-ledger finding extends here: AML evidence and KYC evidence never cross-check; `05-cross-module-sequences.md` §5).
4. **SAR/STR handling is hash-only by design** — `RecordRegulatoryReferenceAsync` accepts only `SAR` or `STR` kinds and stores jurisdiction + a reference **hash** (`FC:/PostgreSqlFinancialCrimeControlPlane.cs:291-305`): no SAR narrative ever enters the platform (data minimization), but also no examiner-facing export of the reference exists.
5. **The integrity machinery that exists is strong** — contiguous per-subject screening versions with replay-conflict detection (`:94-113`), signal idempotency-key hashing with input-match replay checks (`:146-158`), optimistic-version case mutations (`:185-196, 210-213`), Approved-decision single-use consumption windows (`:268-283`), and check-constrained lifetimes (`FC:/FinancialCrimePersistence.cs:115-207`) — the package documents the machinery and the missing pipes that would feed it.
